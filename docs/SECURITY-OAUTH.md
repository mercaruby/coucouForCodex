# Seguridad del inicio de sesión con ChatGPT

Fecha: auditoría OAuth del 1 de octubre de 2026; revisión adicional del consumo del 2 de octubre. Este documento distingue mecanismos comprobados, implementación pendiente y prueba real con una cuenta elegible. La auditoría no lee sesiones de otras aplicaciones, `auth.json`, cookies ni tokens personales. El runtime OAuth propio utiliza y protege las credenciales entregadas por OpenAI tras consentimiento oficial.

## Decisión de arquitectura

Se acepta **la integración OAuth y Responses para el uso personal evaluado**, dentro del modelo de amenaza definido, tras 44 pruebas iniciales de la crate y una aceptación real completada: OAuth oficial Sign in with ChatGPT, credenciales propias en Windows Credential Manager y llamadas directas a Responses. No necesita obtener las credenciales de Codex ni ejecutar `codex app-server` para el chat. El PM confirmó consentimiento, catálogo de cinco modelos y una respuesta mínima completada con `gpt-5.6-luna`; posteriormente confirmó el build release y el arranque de la aplicación.

El flujo público documentado permite registro dinámico y uso del plan tras consentimiento. La conexión se crea para esta aplicación; identidad y permiso de uso del plan son capacidades distintas. Tener una sesión válida no basta para activar inferencia. No se deduce que todas las cuentas o modelos sean elegibles. [Disponibilidad y ejemplo oficial](https://developers.openai.com/cookbook/articles/sign-in-with-chatgpt).

La ruta de inferencia admite exclusivamente `https://api.openai.com/v1/responses`, con `store:false`, `stream:true` y **sin herramientas**. El catálogo procede de `https://api.openai.com/v1/models`. El backend sólo devuelve una respuesta completa cuando recibe `response.completed`; errores, respuestas incompletas o desconexiones no se presentan como éxito. [Modelos e inferencia oficiales](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference).

En esta ruta no existe un ejecutor de shell, MCP, plugins, servidor RPC de herramientas, navegador del agente ni lectura autónoma de archivos. Las instrucciones de un modelo o adjunto no pueden conceder esas capacidades. La monitorización por hooks y las integraciones configuradas por el usuario son subsistemas independientes: no reciben credenciales OAuth del chat ni se invocan como herramientas del modelo.

## Qué protegemos y frente a quién

Activos: tokens de acceso, refresco e identidad propios de esta aplicación; códigos OAuth y verificador PKCE; cuenta/registro seleccionado; mensajes, historial y adjuntos; configuración y credenciales de otras aplicaciones; integridad de los archivos locales.

Se evalúan un modelo o adjunto malicioso, respuestas HTTP o callbacks manipulados, configuración y variables de entorno heredadas, enlaces o nombres de modelo controlados por terceros, IPC incorrecto y otro usuario local de Windows. Se presupone un sistema operativo operativo, bibliotecas criptográficas sin compromiso conocido y un binario construido desde el código revisado.

Malware con acceso al mismo usuario, administradores, un navegador comprometido, una DLL/binario sustituido, fallos desconocidos del sistema o un compromiso del proveedor quedan fuera de esta frontera. Credential Manager protege el almacenamiento, pero no transforma una aplicación del mismo usuario en un secreto inaccesible para todo proceso de ese usuario. No se promete riesgo cero.

**Fuga** significa transmitir credenciales o información a un canal o destino no autorizado. Enviar a OpenAI los mensajes y adjuntos elegidos para obtener una respuesta es parte explícita del servicio. `store:false` no equivale a procesamiento local ni elimina todas las políticas de conservación aplicables.

## Fronteras y condiciones verificables

| Frontera | Vía concreta de fallo | Mitigación exigida y prueba de aceptación |
| --- | --- | --- |
| Autorización | Sustitución de sesión, callback falso, intercambio de un código ajeno | Un intento pendiente con `state`, nonce y verificador PKCE nuevos generados con CSPRNG; desafío S256. Rechazar state incorrecto, duplicado, ausente o de un intento cancelado antes del intercambio. |
| Callback local | Puerto ocupado por otro proceso, listener expuesto a LAN, cabeceras infinitas, parámetros contradictorios | Abrir listener en `127.0.0.1` antes del navegador. Usar `/auth/callback`, URI exacta por intento, método/ruta permitidos y plazo/límites estrictos de lectura. Rechazar parámetros críticos duplicados y solicitudes demasiado grandes. Cerrar listener al finalizar o cancelar. Comprobar exclusividad del bind en Windows o documentar la protección efectiva PKCE/state ante interferencia local. |
| Registro | Usar `dynamic_agent_client` como registro definitivo o sustituir cuenta al reconectar | En registro nuevo, exigir ID emitido válido; en reconexión, conservar el ID esperado y rechazar uno distinto. Mantener la nueva conexión separada de la activa hasta verificar identidad. |
| Identidad | JWT modificado, algoritmo inseguro, claves controladas por el token, cuenta distinta | Verificar firma con biblioteca mantenida y JWKS del emisor oficial; limitar algoritmos; validar issuer, audience del ID emitido, expiración, nonce, sujeto y claims temporales requeridas. No usar URLs `jku`/`x5u` indicadas por un JWT. Rechazar identidad distinta en reconexión. |
| Permiso y facturación | Identidad sin permiso del plan, renovación que retira permiso, cambio oculto a API | Examinar scopes concedidos por la respuesta del token, no por callback ni por preferencias. Exigir permiso directo para inferencia. Catálogo de la cuenta activa; errores de cuota visibles y sin fallback a una clave API. |
| Transporte | Bearer enviado a redirect, proxy heredado o endpoint configurable | URLs HTTPS oficiales constantes; ninguna redirección de peticiones con credenciales. No heredar overrides de endpoints, CA, proxies o tokens de otra app. Cliente HTTP sin proxy de entorno. Limitar tamaño, tiempo y eventos de respuestas. |
| Almacén | Perfil demasiado grande, escritura parcial, manifiesto corrupto o fallback en texto claro | Servicio propio de Credential Manager; chunks versionados dentro del límite real UTF-16; manifiesto pequeño escrito al final como commit. Fallo conserva manifiesto anterior. Lectura valida formato, número de chunks y tamaño total; corrupción devuelve error sin borrar credenciales. No fallback en disco sin cifrado. |
| Refresh | Dos refrescos consumen la misma credencial, rotación no guardada, retry infinito | Exclusión mutua en carga/refresh/commit/cleanup. Guardar sustitución de credenciales antes de reutilizarlas; respetar ventana de refresco del proveedor. No reintentar paralelamente con el token anterior. Un fallo de persistencia o rotación pide reconexión sin revelar contenido. |
| Logout/cancelación | Un login o respuesta tardía resucita la cuenta borrada | Generación de sesión y cancelación compartidas. Login, refresh y turnos tardíos no pueden escribir tras logout/cambio de cuenta. Borrado local comprobado; revocación remota fallida se informa sin restaurar secretos. |
| IPC/WebView | Un comando devuelve el perfil completo o el error contiene tokens | IPC con tipos de respuesta mínimos: estado, identidad validada apta para mostrar, catálogo y texto. Ninguna operación devuelve tokens/códigos/verificador/JWT ni parámetros completos de autorización. HTML remoto no se evalúa; contenido del modelo se inserta como texto. |
| Logs y fallos | Debug de perfil, URL OAuth/callback, body HTTP o error del proveedor | Tipos con secretos sin `Debug`; errores públicos estructurados y genéricos; nada de headers/body/URLs de autorización en logs. Pruebas con marcadores ficticios verifican ausencia de secretos en errores y serialización pública. |
| Historial | Respuesta de cuenta anterior, acumulación sin límite o persistencia inadvertida | Turnos serializados, límites de entrada/historial/salida, generación contra reset/cambio de cuenta y commit sólo después de completar. No enviar historial previo a una cuenta nueva. |
| Adjuntos | Ruta IPC arbitraria, traversal, ADS, archivo enorme o contenido ejecutado | Selección explícita; comprobación del inbox, archivo regular, ruta canónica y límites de tamaño/tipo. Envío como datos. No ejecución ni lectura de referencias a otros archivos que aparezcan dentro del adjunto. |

Los detalles de registro, callback `127.0.0.1`, PKCE, validación del ID token y reconexión proceden de la [guía oficial de registro](https://developers.openai.com/siwc/token-sharing-open-source/sign-in). El token de refresco es separado del token de acceso y se sustituye tras renovación; no se infieren sus valores de claims opacas. [Referencia de tokens](https://developers.openai.com/siwc/token-sharing-open-source/token-reference).

Credential Manager limita `CredentialBlobSize` a **2.560 bytes**. Un JSON con varios JWT no debe guardarse suponiendo que cabe en una sola entrada. Con `set_password`, medir UTF-16 real: 900 caracteres Unicode no garantizan 1.800 bytes. La estrategia propuesta escribe chunks bajo una versión aleatoria nueva, confirma el manifiesto y después limpia la versión antigua; todas estas operaciones se serializan. [Límite de Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentiala).

El mutex sólo asegura exclusión dentro del proceso. La aplicación debe conservar una única instancia de su runtime/almacén; si se permite más de un proceso escritor, hace falta un bloqueo entre procesos. El formato del manifiesto no debe admitir un número de chunks arbitrario, IDs de versión sin validar ni nombres de entradas externos al namespace propio.

La persistencia de `keyring` 3.6.3 para Windows usa `CRED_PERSIST_ENTERPRISE`: en perfiles con roaming puede llevar entradas del mismo usuario a otras máquinas. No supone acceso de otro usuario, pero contradice la identidad por instalación y permite dos escritores del mismo refresh token desde máquinas distintas. La implementación OAuth ahora utiliza WinCred nativo con `CRED_PERSIST_LOCAL_MACHINE` para el host ID y el journal propio, y rechaza entradas de persistencia diferente al leer. No se inventa cifrado: ambas opciones utilizan Credential Manager. [Semántica de persistencia de Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw).

La limpieza de chunks antiguos ocurre después del commit. Un fallo puede dejar entradas residuales protegidas, nunca un archivo en texto claro. No se debe afirmar borrado físico completo ni desconexión persistida si Windows rechazó una operación. Un manifiesto corrupto impide arrancar la conexión: es un fallo seguro, aunque la recuperación necesita instrucciones o una acción específica sobre el namespace propio. No se borra silenciosamente un perfil para ocultar el error. La revocación en ChatGPT sigue siendo la salida si no se puede confirmar la revocación desde la app.

## Comprobaciones y estado

**Comprobado en fuentes primarias:** existe la ruta OAuth local formal sin client secret; se requieren permiso directo y validación criptográfica; el endpoint de inferencia pública requiere streaming y terminal completed. El SDK oficial consultado usa cifrado OS para persistir credenciales, serializa operaciones del almacén y trata el estado de refresh/cambio de cuenta de forma explícita. Consultar código upstream no equivale a haber validado nuestra implementación.

**Comprobado en la adaptación anterior:** 15 pruebas del backend Windows y 6 del relay cubrieron conservación de hooks, configuración corrupta, backups, rutas confinadas, ADS, colisiones de nombres y permisos largos/desconocidos que vuelven al CLI. Esas pruebas no demuestran seguridad ni éxito del OAuth nuevo.

**Inspeccionado en el código nativo nuevo:** `windows/chatgpt-client/src/oauth.rs` genera valores CSPRNG de 256 bits y PKCE S256, preabre loopback, valida parámetros duplicados/state/registro, fija discovery/JWKS y verifica RS256/issuer/audience/nonce/claims temporales/sujeto. El cliente bloquea redirects/proxies de entorno y limita JSON OAuth a 256 KiB; el catálogo tiene su límite separado de 4 MiB y un máximo de 1.000 entradas, porque contiene metadata de capacidades que la UI no consume. `responses.rs` construye el payload sin `tools`, exige SSE y terminal completed y limita eventos/stream/texto. `storage.rs` escribe chunks de 900 unidades UTF-16 y manifiesto versionado al final; tipos de credenciales sin Debug. Esto demuestra controles presentes, no ausencia de todos los fallos.

El wiring de `windows/src-tauri/src/lib.rs` abre la URL oficial desde Rust y devuelve sólo el ID del intento a la WebView. Selecciona explícitamente backend ChatGPT/API; backend desconocido devuelve error. `chatgpt.rs` comprueba la generación de cuenta y la revisión del historial antes del commit. La app conserva CSP local y el texto de respuesta no se interpreta como código.

El ejemplo separado `windows/src-tauri/examples/subscription_smoke.rs` usa el mismo almacén propio, navegador oficial y una sola solicitud mínima. Sólo imprime estado, cantidad de modelos, identificador del modelo y longitud del texto; no imprime tokens, identidad, registro ni conversación. Debe ejecutarse con la app detenida porque no comparte un bloqueo de escritor entre procesos. La revisión del ejemplo no equivale a su ejecución.

El SDK oficial `packages/local/src/responses.ts` documenta que la ruta directa puede devolver SSE válido sin Content-Type. Se revisó la adaptación: solicita `Accept: text/event-stream` y permite cabecera ausente con exactamente el mismo parser limitado y terminal completed obligatorio. Un Content-Type explícito diferente sigue rechazándose; no hay fallback a interpretar HTML o JSON como una respuesta completada. Los diagnósticos muestran sólo código HTTP y una categoría fija de formato, nunca la cabecera literal ni el cuerpo privado.

También se revisó la compatibilidad con texto entregado exclusivamente en `response.output_text.delta`, como hace el SDK oficial. Se acumulan strings con límite agregado de 1.000.000 bytes, pero no se devuelven ni se guardan en historial hasta `response.completed` con status completed, sin error y estructura válida. El texto final es autoritativo si existe; el acumulado sólo sustituye texto final ausente. Un terminal con herramientas, rechazo, contenido inválido o salida demasiado grande sigue produciendo error, al igual que EOF/failed/incomplete antes del terminal. La adaptación no imprime fragments ni cuerpos privados para diagnosticar el formato.

Revisión acotada de dependencias contra [RustSec](https://github.com/RustSec/advisory-db), 1 de octubre: el lock usa rand 0.8.8, ring 0.17.14, rustls-webpki 0.103.15 y rustls 0.23.45; incluyen los parches publicados para esas ramas, incluido RUSTSEC-2026-0285 de septiembre. No se encontraron entradas de paquete jsonwebtoken/reqwest/keyring en esa base. No se realizó cargo-audit de todo el árbol ni se concluye ausencia de vulnerabilidades desconocidas.

La primera ejecución independiente obtuvo **30/32 pruebas pasando** y descubrió dos fallos: el socket aceptado heredaba nonblocking en Windows y logout conservaba la sesión en memoria si fallaba persistir el perfil desconectado. Ambos se corrigieron y la nueva ejecución obtuvo **44/44 pasando**: 38 casos independientes adversariales y 6 básicos. Incluyen callback positivo sobre sockets reales Windows, lectura lenta con plazo absoluto, cancelación, JWT firmado sintético, SSE, corrupción/Unicode/transacciones del journal, scopes, proyección pública, fallo al persistir logout e invalidación mientras el gate está ocupado. Consultar comandos y casos en `VALIDATION-OAUTH.md`.

El código final invalida generación y memoria antes de esperar al gate de autenticación. Retira duraderamente el grant de refresh anterior antes de consumirlo, guarda un checkpoint protegido de la rotación antes de validar metadata/identidad y respeta earliest_refresh_at. Una respuesta perdida o inválida obliga a reconectar; el grant anterior no se vuelve a usar. Pending refresh no anuncia permiso de uso del plan. Una carrera con logout o una revocación no confirmada produce instrucciones para revocar en ChatGPT, no una afirmación de éxito remoto.

Los cinco casos de regresión añadidos durante la aceptación real cubren deltas con completed sin texto final, rechazo de terminal ausente/erróneo/failed/incomplete/error/herramienta/rechazo/malformado, límites agregados Unicode y salida final sin fallback ante exceso, clasificación MIME sin reflexión de cabeceras y catálogo de 300 KiB con límite separado y rechazo al excederlo. Pasan en la nueva ejecución locked de 44 pruebas.

Las pruebas no simulan la transacción HTTP completa de refresh ni la carrera remota de revocación; esos caminos se inspeccionaron en código. La verificación JWT usa una clave pública sintética, no una descarga real de JWKS. Los tests del journal usan almacenamiento en memoria. Un test nativo adicional escribe exclusivamente una entrada propia `test:<aleatorio>` con valores ficticios, verifica LOCAL_MACHINE, vacío y Unicode de exactamente 2.560 bytes y elimina la entrada; no consulta credenciales personales. También se revisaron tamaño/paridad/puntero nulo/persistencia en el wrapper WinCred. No se han probado aquí corrupción del sistema operativo, cambios reales de permisos del proveedor ni rotación de claves en producción.

**Aceptación real comunicada por el PM, 1 de octubre:** el usuario completó el consentimiento en el navegador oficial. El ejemplo separado terminó con código 0 y los marcadores `OFFICIAL_CONSENT_VERIFIED`, `OFFICIAL_PLAN_CONNECTED` (cinco modelos) y `SUBSCRIPTION_INFERENCE_COMPLETED` (`gpt-5.6-luna`, dos bytes de texto). Esto confirma una respuesta completada en la ruta OAuth propia para esa cuenta. No se inspeccionaron ni copiaron tokens mediante herramientas de auditoría, ni se leyeron sesiones de otras aplicaciones. No constituye una auditoría forense de facturación ni demuestra elegibilidad universal de planes, cuentas o modelos.

El PM también comunicó frontend final aprobado y **73 pruebas de workspace pasando**: 44 de OAuth, cuatro del protocolo anterior, 19 de la aplicación y seis del relay. Esas pruebas no ejecutan por sí mismas el consentimiento o inferencia real y se distinguen del resultado del ejemplo.

**Criterios de aceptación y cobertura:** los puntos 1–6 están cubiertos por pruebas de fixtures y revisión de código con los límites anteriores. La parte OAuth/inferencia real del punto 7 pasó. El PM confirmó después el build release, arranque sin un nuevo fallo de ventana de ajustes y entrega de eventos sintéticos por el relay. Esta comprobación no automatiza toda la interfaz ni demuestra todas las carreras remotas:

1. Pruebas negativas state/nonce/issuer/audience/exp/firma/algoritmo, scopes ausentes y cambio de client ID/sujeto. Un JWT decodificado sin verificación no pasa.
2. Callback con parámetros duplicados, cancelación, puerto en uso, request grande y lectura que no termina. Ninguna de estas entradas debe llegar al intercambio.
3. Almacén de tokens ficticios grande, Unicode, manifiesto corrupto, chunk perdido y fallo de escritura antes del commit. Perfil anterior conservado o error seguro; cero fallback en texto claro.
4. Dos solicitudes simultáneas al refresco; logout/cambio de cuenta mientras login/refresh/inferencia está pendiente; comprobar que ninguna conexión antigua reaparece.
5. SSE con chunks divididos, evento failed/incomplete, límite de tamaño, desconexión antes de completed y respuesta de herramienta. No se ejecuta acción, no hay éxito parcial ni commit del historial.
6. Inspección final de payloads/IPC/logs: `tools` ausente, `store:false`, `stream:true`, endpoints constantes, redirects/proxies desactivados y secreto ficticio ausente de errores públicos.
7. Build nativo y arranque de WebView. Después, con autorización y una cuenta elegible, login oficial y una inferencia mínima completada. Sin esa última prueba se describe como integración implementada y probada con fixtures, no como uso real del plan confirmado.

No se utilizarán credenciales reales para las pruebas negativas. Los endpoints ficticios sólo pueden existir en el código de pruebas; la build de producción no debe ofrecer un override secreto que permita enviar un bearer a otro servidor.

## Consulta independiente del consumo de Codex

`windows/src-tauri/src/usage.rs` consulta metadatos de la sesión propia de la CLI oficial de Codex; este consumo se etiqueta como **Codex**, separado de los límites de uso de esta aplicación mediante SIWC. Una cuota comunicada por Responses no se convierte en un porcentaje global inventado. Las cuentas activas de Codex y SIWC pueden ser distintas; el lector no obtiene identidad para vincularlas y no supone que coincidan.

El mensaje `subscription_sharing_usage_limit_exceeded` indica un límite comunicado por OpenAI para la aplicación o cuenta. `subscription_sharing_usage_unavailable` indica que no se pudo comprobar uso y recomienda reintentar conservando la conexión. HTTP 429 informa de un límite de uso o frecuencia de esa petición. Ninguno de estos errores revela el cuerpo privado, recomienda extraer tokens ni inicia otro OAuth automáticamente. Se retiraron los sufijos técnicos HTTP/MIME del texto mostrado al usuario; siguen vigentes límites y validación SSE. Dos pruebas de estas propiedades pasaron con fixtures sintéticos.

El ejecutable se resuelve por ruta absoluta canónica y cabecera PE con offset limitado. La autodetección se restringe a ubicaciones de instalación conocidas: la CLI extraída por la app Desktop bajo LOCALAPPDATA/OpenAI/Codex/bin (hasta 64 entradas de versión de 16 caracteres hexadecimales), paquetes npm de OpenAI y USERPROFILE/.codex/bin. La candidata de `.tools` sólo existe en debug y procede de una ruta fija de compilación, no del directorio actual. Una ruta explícita es una decisión de confianza del usuario: una cabecera PE no acredita autoría, firma o integridad de OpenAI. No se ejecutan wrappers Node, scripts, una búsqueda de PATH ni una shell para esta consulta.

El hijo arranca oculto, desde el directorio de Windows obtenido por API, con entorno vaciado y lista OS/CODEX_HOME. No hereda claves API, proxies ni overrides de Node/proveedor por variables. Se fija `model_provider="openai"`, se elimina el override ordinario de `openai_base_url` y se fija `chatgpt_base_url` oficial. Se conservan la autenticación y políticas administradas de la CLI: Codex puede usar o renovar internamente su sesión propia, pero la adaptación no lee/copia `auth.json`, cookies, tokens ni historial de Codex y no los entrega a la WebView. No hay implementación de HTTP privado en el lector.

La secuencia RPC es exclusivamente initialize → initialized → account/rateLimits/read, con `excludeResetCreditDetails:true` y sin activar Luna Reserve. No se envían thread/start, turn/start, ejecución de comandos, aprobaciones, lecturas de historial ni solicitudes de herramientas. Una petición iniciada por el servidor se rechaza. El servidor oficial contiene más capacidades, pero el lector no ofrece un proxy genérico hacia ellas.

Se revisó en el código oficial 0.159.2 que el arranque del app-server también refresca el catálogo de modelos en segundo plano. Por eso se aíslan cwd, entorno y destinos ordinarios; no debe describirse esta ejecución como ausencia absoluta de toda actividad de red aparte del RPC. Se confía en el binario oficial y las políticas administradas del equipo dentro del modelo de amenaza.

El lector limita toda la transacción a 20 segundos, cada línea a 256 KiB, salida a 2 MiB y mensajes a 64. Consulta bytes disponibles mediante PeekNamedPipe antes de leer, evita un thread de lectura bloqueado y ejecuta kill/wait al liberar su hijo. Las escrituras RPC son constantes pequeñas. No se imprime stderr ni se reflejan errores o mensajes del protocolo en UI. Sólo se proyectan buckets/ventanas con métricas válidas y etiquetas acotadas; campos desconocidos, identidad y credenciales no se serializan.

La caché serializa consultas, conserva resultados durante 60 segundos y aplica mínimo de 15 segundos al refresco explícito. Tras error, un resultado previo se marca stale y conserva su fecha; cambiar ruta de CLI descarta el snapshot anterior. Los valores nulos o inválidos siguen desconocidos y un mapa de buckets explícitamente vacío no se reemplaza por datos legacy.

**Aceptación de esta ampliación:** el integrador/validador comunicó 18 pruebas del lector pasando, incluidos timeout, flood, error privado, límites/valores nulos, PE y caché. La prueba real explícita, ignorada en la suite rutinaria, pasó en 0,76 segundos y devolvió dos ventanas con métricas válidas. Este documento omite sus valores privados. No inició otro login, OAuth, conversación ni inferencia. Este resultado no mide la cuota SIWC de Coucou ni el porcentaje global del plan, y puede cambiar después de la consulta. La auditoría acepta el lector dentro de las fronteras descritas; compilación release y comprobación final de UI corresponden al PM.

## Recuperación de un almacén propio corrupto

Un error al leer el manifiesto o una parte impide activar la conexión; no autoriza texto claro ni importar una sesión de Codex. Si el runtime no se pudo crear, los botones normales Disconnect/Reconnect no pueden reparar ese estado. La recuperación manual actual es:

1. Cerrar Coucou Codex, incluido su proceso de bandeja, y cualquier ejemplo `subscription_smoke`. No reparar mientras otro proceso escribe el journal.
2. Abrir [Manage usage de ChatGPT](https://chatgpt.com/settings/usage) y revocar el acceso de **Coucou Codex** si no se pudo confirmar revocación desde la aplicación. Esto no exige entregar un token a ninguna herramienta.
3. Abrir el Administrador de credenciales de Windows, sección Credenciales de Windows / Credenciales genéricas. Revisar únicamente entradas cuyo nombre empieza exactamente por **`local.coucou-codex.chatgpt:`**. El formato es `local.coucou-codex.chatgpt:record-index` y `local.coucou-codex.chatgpt:record:<versión>:<número>`; eliminar el índice y todas sus partes, incluidas versiones residuales dentro de ese mismo namespace.
4. Normalmente conservar `local.coucou-codex.chatgpt:host-id`. Si el error identifica el host ID corrupto, eliminar también esa entrada propia. Regenerarlo crea una identidad de instalación nueva y puede producir un registro de aplicación nuevo en ChatGPT; revisar y revocar allí el anterior. Quitar el journal ya descarta el registro guardado, por lo que también puede requerir consentimiento nuevo.
5. Reiniciar la app e iniciar sesión de nuevo mediante el navegador oficial. Si Windows vuelve a rechazar operaciones, conservar el error y corregir el acceso a Credential Manager; no crear archivos de tokens ni reutilizar credenciales de otras aplicaciones.

Las entradas del servicio `local.coucou-codex` usado para claves API/integraciones son distintas. No borrar entradas de Codex, ChatGPT, OpenAI u otras aplicaciones por semejanza del nombre. La recuperación pierde sólo la conexión propia seleccionada; no demuestra borrado forense de copias previas del sistema operativo ni de otros dispositivos.

## Alternativa app-server, si vuelve a ser necesaria

Se revisó el código oficial tag `rust-v0.159.2`, commit `ff6aec96948b70d94983af2641a6b67c94faeff5`. `ThreadStartParams.environments` distingue omitir el campo de un array vacío: el array vacío deshabilita acceso a entornos. `spec_plan.rs` condiciona shell, apply_patch y view_image a que haya entorno. Esta es una alternativa concreta a depender únicamente de un campo `readOnly.access` que el binario instalado no publica.

No se aprueba quitar el gate para usar simplemente `readOnly`: lectura global, configuración heredada, MCP/apps y otros mecanismos no quedan eliminados con ese nombre. Una alternativa app-server necesitaría verificar en el binario efectivo la ausencia de entornos y herramientas, un `CODEX_HOME` propio, entorno limpio, rechazo de RPC, cuentas oficiales y config efectiva sin MCP/plugins/hooks. El cargador oficial puede recibir capas de sistema/administración además del perfil de usuario: un directorio nuevo por sí solo no elimina esas capas.

La decisión actual de usar OAuth formal + Responses sin herramientas elimina ese problema del chat y no requiere ejecutar el CLI, copiar su autenticación ni exponer tokens mediante app-server.
